# 職歴と実績は秘匿化の有無で出し分け、限定公開は職務経歴書だけが持つ

## Context and Problem Statement

[ADR-0008](./0008-content-visibility.md) は、コンテンツの可視性を公開・限定公開・非公開の 3 段階で扱い、経歴（career / project）は 3 段階すべてを取ると決めた。公開できる値と公開できない値は、同じレコードの別のカラムとして対（`client` / `clientPublic`）で持つ。internal のコンテンツは公開前の下書き状態を持ち、公開済みのものは削除せずに非公開へ戻せる。

ADR-0008 が挙げた、公開しない状態を必要とする理由は 3 つある。

1. internal の記事に、公開前の下書き状態が要る
2. 経歴には、そのまま公開できない情報が含まれることがある
3. センシティブな情報が見つかったとき、削除以外の方法が要る

経歴には、商談の相手にだけ開示する場面もある。

[#72](https://github.com/ksyunnnn/synsk.me/issues/72) で、オーナーは次のことを決めた。どれも ADR-0008 の「経歴は 3 段階すべてを取る」と食い違う。

- 実績は訪問者に出すかどうかで分けず、秘匿化した値で出すか、実際の値で出すかで分ける（[6380570672](https://github.com/ksyunnnn/synsk.me/issues/72#issuecomment-6380570672)）。列は project.is_masked の 0・1（[6381465201](https://github.com/ksyunnnn/synsk.me/issues/72#issuecomment-6381465201)）
- 職歴も実績と同じく職務経歴書の外に出し、career.is_masked で秘匿化する（[6409375752](https://github.com/ksyunnnn/synsk.me/issues/72#issuecomment-6409375752)）
- 「限定公開」という言葉は職務経歴書にだけ使う（6380570672）。実績 1 件ごとに渡すリンクは持たない（[6332023046](https://github.com/ksyunnnn/synsk.me/issues/72#issuecomment-6332023046)）
- 学歴は職務経歴書を通してだけ出し、見せるかどうかの列を持たない（[6408900481](https://github.com/ksyunnnn/synsk.me/issues/72#issuecomment-6408900481)）
- 職務経歴書は限定公開用と公開用に分かれ、作ったときに決まり、あとから変えられない（[6249488541](https://github.com/ksyunnnn/synsk.me/issues/72#issuecomment-6249488541)）

2026-11-04 に、オーナーは次のことを決めた。

- 職歴と実績は、既定で秘匿化する
- 秘匿化した職歴・実績で訪問者に出してよい値は、秘匿化した題・秘匿化した組織名・期間・種類・肩書・使ったスキルだけ。説明文は伏せた見た目で出し、本文の画像と関連 URL は出さない
- 公開用の職務経歴書でも、秘匿化しない職歴・実績は実際の値で載せる。秘匿化したものだけを秘匿化した値で載せる
- 職歴と実績は、サイトに載せるかを `status`（`draft`・`published`）で 1 件ずつ持つ。既定は `draft`。`draft` の職歴・実績は、管理画面と、限定公開用の職務経歴書を作るときにだけ使う。`status` は `is_masked` とは別の軸で、`published` の職歴・実績を実際の値で出すか秘匿化した値で出すかを `is_masked` が決める

最後の決定は、#72 の「実績は訪問者に出すかどうかで分けない」（6380570672）を覆す。訪問者に見せるかを `status` で表すのは、[ADR-0043](./0043-d1-column-naming.md) の決まりに従う。

対の値の名前は、[ADR-0043](./0043-d1-column-naming.md) が `_masked` の接尾辞に揃えた。

ADR-0008 のうち、note の下書き、公開済みを削除せずに戻せること、対の値を同じレコードに持つことは、#72 の決定と食い違わない。[docs/decisions/README.md](./README.md) は覆すときに新しい記録を書くと定め、一部だけを覆すときも元の記録をまるごと引き継ぐ（[#72 のコメント 6231369601](https://github.com/ksyunnnn/synsk.me/issues/72#issuecomment-6231369601)）。

## Decision Drivers

* [対話 over 展示](../PRINCIPLES.md#4-対話)
* 取引先などの実際の値は、一度訪問者に出ると取り消せない
* 訪問者に見せるかは `status` で表す（[ADR-0043](./0043-d1-column-naming.md)）

## Considered Options

* 公開 / 非公開の 2 段階
* 非公開データを別ストアに隔離する
* 3 段階 + 同一レコードで保持（ADR-0008 の形）
* 見せ方を種類ごとに分け、限定公開は職務経歴書だけが持つ + 同一レコードで保持

## Decision Outcome

Chosen option: "見せ方を種類ごとに分け、限定公開は職務経歴書だけが持つ + 同一レコードで保持", because 職歴と実績は秘匿化した値で訪問者に出せば、取引先の実際の値を出さずに経歴を並べられ、商談の相手に開示する場面は限定公開用の職務経歴書が受け持つため。サイトに載せない職歴・実績は `draft` にすれば、行を消さずに訪問者から隠せ、限定公開用の職務経歴書の材料に残せるため。

**note**

- note は下書きと公開の状態を持つ。訪問者に見せるのは公開の note だけ
- 公開した note は、削除せずに下書きへ戻せる

**職歴と実績**

- 職歴と実績は、サイトに載せるかを `status` で 1 件ずつ持つ。`published` はサイトに載せ、`draft` は載せない。既定は `draft`
- `draft` の職歴・実績は、秘匿化するかどうかに関わらず、訪問者への応答に含めない。管理画面と、限定公開用の職務経歴書を作るときにだけ使う
- 職歴と実績は、秘匿化するかどうかを 1 件ずつ持つ。既定は秘匿化する
- `status` と秘匿化するかどうかは別の軸である。`published` で秘匿化しない職歴・実績は、実際の値で出す
- `published` で秘匿化した職歴・実績は、秘匿化した題と秘匿化した組織名で出す。訪問者に出してよい値は、秘匿化した題・秘匿化した組織名・期間・種類・肩書・使ったスキルだけ。説明文は伏せた見た目で出し、中身を訪問者への応答に含めない。本文の画像・代表画像・関連 URL を出さない
- 公開できる値と公開できない値は、同じレコードの別の列として対で持つ（organization.name と organization.name_masked、project.title と project.title_masked）。説明文の秘匿化した値は持たない
- 学歴は職務経歴書を通してだけ出し、見せるかどうかを 1 件ずつ持たない

**職務経歴書**

- 「限定公開」は職務経歴書だけが持つ。職歴・実績・note に 1 件ごとの限定公開を持たない
- 職務経歴書は、作るときに限定公開用か公開用かを決め、あとから変えない
- 限定公開用は、秘匿化した職歴・実績と `draft` の職歴・実績も、実際の値で載せられる
- 公開用は、`published` の職歴・実績だけを載せる。秘匿化しない職歴・実績を実際の値で、秘匿化した職歴・実績を秘匿化した値で載せる
- 職務経歴書は下書きと、訪問者に見せる状態を持つ

限定公開用を閲覧させる仕組み（URL・期限）は、この記録の対象ではない。

### Consequences

* Good, because 職歴と実績を一覧と個別のページに並べても、秘匿化したものの取引先の実際の値は訪問者に出ない
* Good, because 商談で経歴を開示する運用を、限定公開用の職務経歴書で行える。職歴・実績の 1 件ごとに開示先を管理しない
* Good, because note は公開後に判断が変わっても、データを失わずに取り下げられる
* Good, because 職歴と実績を、行を消さずに `draft` にして訪問者から隠せる。隠した職歴・実績も、限定公開用の職務経歴書に載せられる
* Bad, because 秘匿化しても、`published` の職歴・実績の期間・種類・肩書・使ったスキルは出る
* Bad, because 訪問者向けの取り出しは、`status` と `is_masked` の 2 つを条件にする。`status` の条件を書き漏らすと、`draft` の職歴・実績が訪問者に出る
* Bad, because 配信物を生成する処理が、出す値と出さない値を選別する必要がある
* Bad, because 選別の対象が増えるため、カラムを追加するたびに判断が発生する
* Bad, because **選別の漏れ。** 除外リスト方式（これを除く）にすると、カラムが増えたときに漏れる。許可リスト方式（これだけを出す）であれば、新しいカラムは既定で公開されない

### Confirmation

career と project が is_masked と status の列を持つこと、education が見せるかどうかの列を持たないこと、resume が限定公開用か公開用かの列（resume.audience）を持つことは、`migrations/` の CREATE TABLE で確かめられる。

秘匿化した職歴・実績の実際の値が訪問者への応答に含まれないことは、判定手段を定めていない。応答を作る処理は、この記録の時点でリポジトリにない。

## Pros and Cons of the Options

### 公開 / 非公開の 2 段階

* Good, because 単純。フラグ 1 つで表現できる
* Bad, because 商談の相手にだけ経歴を開示する場面が表現できない

### 非公開データを別ストアに隔離する

公開用ストアには公開可のものしか入れない。

* Good, because 公開側に非公開データが存在しないため、フィルタの実装ミスによる漏洩が起きない
* Bad, because 1 件の案件情報が 2 つのストアに分かれ、実際の値と秘匿化した値の対応関係を手で維持することになる

### 3 段階 + 同一レコードで保持（ADR-0008 の形）

* Good, because 案件情報が 1 か所にまとまる。可視性がカラムの構造そのもので表現される
* Bad, because 職歴・実績に 1 件ごとの限定公開を持つと、職務経歴書の限定公開と、開示先を 2 か所で決めることになる
* Bad, because 非公開の職歴・実績は一覧に出ず、秘匿化した値で並べる見せ方が表現できない

### 見せ方を種類ごとに分け、限定公開は職務経歴書だけが持つ + 同一レコードで保持

* Good, because 案件情報が 1 か所にまとまる
* Good, because 開示先を決めるのは職務経歴書だけになる
* Good, because 職歴・実績を残したまま、`draft` にして訪問者から隠せる
* Bad, because 職歴・実績が、サイトに載せるかと秘匿化するかの 2 つの列を持つ
