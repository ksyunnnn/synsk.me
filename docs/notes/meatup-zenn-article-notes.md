## 3. 各セクションの素材（事実）

### 背景・動機
- 友達と「meatup」という肉を囲むゆる交流イベントを開催（2018→2019→**6年ぶりに2026夏**復活）。
- 招待制で参加者管理したい：誰が来るか・確定/未確定・事前決済の有無・当日の盛り上げ。
- 過去回サイト（2018/2019）は `meatup.love` のサブドメインで生きてる＝今回は apex に2026を出す。

### 作ったもの（機能）
- **招待制チケット管理サイト**。動線：招待リンク `/invite` → サインイン → 登録 `/register` → **マイページ `/mypage`（実務ホーム）** → **チケット `/ticket`（“券のリビール”＝盛り上げ用）**。
- **仮想チケット**：名前・肩書き・No.・QR・「楽しみ(肉/麦/遊/繋)」の透かし入り横長デザイン。現場では使わない“映え”用。
- **個別チケットのOGP画像を動的生成**（共有するとその人専用のチケット画像がカードに出る）。
- **admin 画面**：承認(確認しました)・招待発行・支払い管理・性別付与・「楽しみ」集計。
- 会場紹介セクション・参加費・連絡導線(LINE/IG/X)。
- デモ: https://meatup.love（トップは公開、内部は要サインイン）

### 構成・技術スタック（なぜ選んだか）
- **Next.js 16 App Router / `output: 'export'`（完全静的）** — 静的書き出しなので **Cloudflare Pages にそのまま乗る**。SSRサーバ不要。
- **React 19 / TypeScript**。
- **Tailwind v4（ゼロランタイム）** — ブランドトークンは `globals.css` の `@theme` が真実の源。
- **Firebase**：Auth（Google ＋ **メールリンク=パスワードレス**）／ Firestore。認可は **`firestore.rules`** で強制。
- **Cloudflare Pages**（ホスティング）＋ **Pages Functions**（個別チケットOG画像を `workers-og`/Satori でエッジ生成、QR付き）。
- 見出しフォントは `next/font/local`（self-host＝ビルド時ネットワーク非依存）。
- ※「サーバ持ちたくない／無料〜激安で運用したい個人開発」にハマる構成。

### やったこと（流れ）
- ログイン後の実務は `/mypage` に集約、`/ticket` は“見せる/共有する瞬間”だけに分離（役割で画面を分ける）。
- 招待は「運営発行=自動確定／確定者発行=要確認」。紹介ツリーを自動追跡。
- OG画像は券面と同一意匠をエッジで動的描画（公開投影 `shares/{uid}` だけ読む）。
- デザイン判断は Apple HIG ＋ WCAG を基準に固定（モーダルvsページ等は**その場で公式を取得して裏取り**）。

### ハマったとこ（←ここが読みどころ。実際に踏んだやつ）
1. **メール認証リンクが1日5通で枯渇**。Spark(無料)はメールリンク送信 **5通/日**。テストで `+1`/`+2`… と試してたら即 `auth/quota-exceeded`。Blaze(従量)で **25,000/日**。※「無課金に人権はないんか？」ネタが使える。エラー文言もコード別に出し分けた。
2. **static export だと `robots.ts`/`sitemap.ts` に `export const dynamic = 'force-static'` が要る**（無いとビルドこける）。
3. **`next/image` を static export で使うなら `images: { unoptimized: true }`**（最適化APIが無いので画像は事前に縮小して `public/` へ）。
4. **「リロードで直る」系の認証バグ**。`onAuthStateChanged` の購読が**初回コールバックしか反映しない**実装になってて、メールリンク完了/ログアウト/アカウント切替が**リロードするまでUIに出ない**。購読は“毎回”反映が正解（初回ガードはタイムアウト調停だけに使う）。
5. **OGキャッシュ沼**。個別OG画像を1年 immutable キャッシュにしてたら、データ更新後も**古い画像が居座る**。→ 画像URLを **`/og/{uid}?v={ticketNo}`** で版管理（ハッシュ付きアセットの発想）。さらに **X はページURL単位でカードをキャッシュ**するので、共有URLも **`/t/{uid}?t={ticketNo}`** に。**2層**で無効化。
   - おまけ凡ミス：共有テキストに「トップURL」と「チケットURL」を2つ入れたら、X が先頭のトップURLをカード化して**チケットのOGが出ない**事故。URLは1本に絞るのが正解。
6. **SNSアプリ内ブラウザ**。Instagram等のWebViewは **Google OAuth を拒否**（`disallowed_useragent`）・メールリンクも別ブラウザに着地して詰む。**確実に外部ブラウザを強制起動する手は無い**（iOSは特に）。検出して「⋯→ブラウザで開いて」と案内するのが現実解。
7. **iOS Safari の動的ツールバー**問題は `min-h-lvh` ＋ in-flow の border で回避。
8. **セキュリティ（Firestore rules）**。招待トークンの“使い切り”をクライアントの transaction だけに頼ってたら、**SDKを介さない直接書き込みで1本のトークンから無制限に自己承認**できた。→ ルールで **`getAfter()` を使い「承認付き作成＝同一コミットで `usedBy==自分` になること」に束縛**して封鎖。PII（連絡先/性別/アレルギー）は世界公開の `shares` 投影に出さず `attendees` は本人/admin のみ、という**コレクション分離**設計も効いた。

### Claude Code、だいすきやった（体験・正直評価）

**★ 著者の実感＝記事の主軸（本人談）**
- **CLIだから“ほとんど”を丸ごと任せられた**。ビルド・git・デプロイ・Firestoreルール適用・OG関数・データ操作の手順まで、作業が **CLI/ファイルで完結**する＝Claude Code が端末内でそのまま実行できた。GUIポチポチ作業だと委任できないが、**CLI中心の構成だと“相棒に丸投げ”が成立**する。← ここが「だいすき」の核。
- **1サイトじゃなく、複数サイト（歴代回）のドメイン/デプロイ層ごと任せられた**。`meatup.love` は apex=2026・`2018.meatup.love`・`2019-summer.meatup.love` を1ドメインに束ねる**ハブ構成**。`wrangler pages deploy` をプロジェクト別に、`firebase deploy --only firestore:rules`、ルーティング/ランブックのドキュメント整備まで、**横断のデプロイ運用を丸ごと**任せられたのが印象的。
- ※正直な線引き（書くと誠実で刺さる）：**Cloudflare の DNS作成(zone:edit)・課金(Blaze化)・OAuth同意画面・本番Firestoreの実データ操作**などは権限/GUI都合で**人間が実施**。“ほとんど”であって全部ではない。CLI/API で完結する所はAIに、ダッシュボード/支払い/最終承認は人間に、という分担。

- **任せた範囲が広い**：設計相談 → 実装 → デバッグ → セキュリティ監査 → SEO/OGP整備 → デプロイ手順 → **この記事のネタ整理まで**。
- 良かったとこ（具体で）：
  - 「リロードで直る」バグを**購読の取りこぼしと一発で特定**。
  - OGキャッシュを**2層（画像 `?v=` ＋ 共有URL `?t=`）で無効化**する設計を提案。
  - モーダルvsページを **HIG/W3Cをその場で取得して根拠ベースで判断**（記憶で語らない）。
  - **サブエージェントで firestore.rules をセキュリティ監査**しながら並行でデプロイ、みたいな“分担”ができた。
- 正直なとこ（等身大に）：
  - 共有URL2本入れて**OGカードを奪われる凡ミスをAI自身がやった**→指摘で即修正。完璧ではない。
  - **最終判断・文言の好み・デザインの匙加減は人間が握る**必要があった（「ちょい殺風景」「これキモい」みたいな感覚は人間が補正）。
  - **デプロイ・Firestoreデータ操作・課金(Blaze)は権限的に人間**がやる場面。
- ワークフロー：会話で小さく刻んで **dev サーバ見ながら即デプロイ**、git は main 直運用。「壁打ち→すぐ反映」が気持ちよかった。
