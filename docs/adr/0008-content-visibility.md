# ADR-0008: コンテンツの可視性を3段階で扱う

> この文書は決定を記録する。有効な要件は持たない。

- **Status**: accepted
- **Date**: 2026-08-21
- **Deciders**: synsk
- **Related Principles**: [対話 over 展示](../PRINCIPLES.md)

---

## Context

[ADR-0003](./0003-content-data-model.md) は「Career + Project + Activity の3テーブル構成」を決定したが、その中に「公開設定」として別の決定が同居していた。

> 雇用関係のクライアント: 会社名を公開
> 業務委託のクライアント: 業界名でぼかす（`client` vs `clientPublic`）

これは [docs/adr/README.md](./README.md) が定める ADR の単位に反する。本 ADR は可視性の決定を切り出し、あわせて 2026-08-21 の検討で判明した論点を含めて決め直す。

検討で挙がった、公開しない状態を必要とする理由は3つ。

1. internal の記事に、公開前の下書き状態が要る
2. 経歴には、そのまま公開できない情報が含まれることがある
3. センシティブな情報が見つかったとき、削除以外の方法が要る

3つめは公開したあとに判断が変わる場合であり、データを保持したまま出す／出さないを切り替えられる必要がある。

さらに、経歴には商談の相手にだけ開示する場面がある。公開と非公開の2段階では表現できない。

---

## Decision

**コンテンツの可視性を、公開 / 限定公開 / 非公開の3段階で扱う。公開できる値と公開できない値は、同一レコードの別カラムとして対にして保持する。**

- 経歴（career / project）は3段階すべてを取る
- 公開できない値と公開できる値は、`client` / `clientPublic` の形で対にする
- internal のコンテンツは、公開前の下書き状態を持つ
- 公開済みのものは、削除せずに非公開へ戻せる

限定公開を閲覧させる仕組み（認証、共有リンク）は本 ADR の対象ではない。

---

## Alternatives Considered

### Option A: 公開 / 非公開の2段階

- **Pros**: 単純。フラグ1つで表現できる
- **Cons**: 商談の相手にだけ経歴を開示する場面が表現できない

### Option B: 非公開データを別ストアに隔離する

公開用ストアには公開可のものしか入れない。

- **Pros**: 公開側に非公開データが存在しないため、フィルタの実装ミスによる漏洩が起きない
- **Cons**: 1件の案件情報が2つのストアに分かれ、`client` と `clientPublic` の対応関係を手で維持することになる

### Option C: 3段階 + 同一レコードで保持 — 採用

- **Pros**: 案件情報が1箇所にまとまる。可視性がカラムの構造そのもので表現される
- **Cons**: 配信物を生成する側が、出す値を選別する責任を負う

---

## Consequences

### Positive

- 商談で経歴を開示する運用を、データ構造の変更なしに後から実装できる
- 公開後に判断が変わっても、データを失わずに取り下げられる

### Negative

- 配信物を生成する処理が、出す値と出さない値を選別する必要がある
- 選別の対象が増えるため、カラムを追加するたびに判断が発生する

### Risks

- **選別の漏れ。** 除外リスト方式（これを除く）にすると、カラムが増えたときに漏れる。許可リスト方式（これだけを出す）であれば、新しいカラムは既定で公開されない
